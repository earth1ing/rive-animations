# Inside `.libraries`

> **Nothing here is yours to edit, and nothing should be built on it.**
>
> `.libraries/` is working storage the tool writes and rewrites. An edit
> inside it is picked up by a running build, which makes it look like a place
> to work, and is then lost the moment that content is downloaded again, with
> nothing reporting it. Delete the folder and a `rive pull` rebuilds it.
>
> This page describes the shape as of `lockVersion: 1`, for anyone who wants
> to know what a `rive pull` left behind. It is not an interface. Expect it to
> change, and do not write anything that reads it.

What a project does with libraries, and the `libraries:` block that names
them, is in [rive-yaml.md](rive-yaml.md).

## The shape

```
myproject/
  rive.yaml
  scene.rml
  .libraries/
    lock.yaml
    bonhomme_eye@118810/
    bonhomme_eye@118811/
    bonhomme_head_and_hat@118813/
```

One folder per **snapshot**, plus a lock file. A snapshot is the content one
publish of a library produced, converted to markup. The folder is named for
the library and the backend's id for that snapshot, after the `@`.

A library appears more than once when the project reaches more than one of
its publishes, which is why `bonhomme_eye` is here twice.

## A snapshot folder

```
bonhomme_head_and_hat@118813/
  rive.yaml
  scene.rml
  faceimage.png
```

It looks like a rive-cli project and is not one. The `rive.yaml` holds a name
and the main artboard, and nothing reads it: the build finds the markup by
scanning for `.rml` and identifies the snapshot by the folder name. It is
there so someone opening the folder can see what they are looking at.

**Do not run `rive` on one.** A snapshot that imports another library names it
the way any document does, and the content it names lives in the **host's**
`.libraries`, not inside the snapshot. So the snapshot alone cannot resolve
its own imports:

```xml
<!-- in bonhomme_head_and_hat@118813/scene.rml -->
<LibraryAsset libraryId="623" libraryVersionId="1645" assetId="118810" name="bonhomme_eye"/>
```

`bonhomme_eye@118810` is a sibling of that folder, not a child. Only the
project at the root holds the whole graph.

## `lock.yaml`

Everything a snapshot cannot say about itself. The snapshot's bytes never
mention which library or version they belong to, and the folder name carries
only the snapshot id, so the lock is what joins them up.

```yaml
# Generated by Rive CLI. Do not edit
lockVersion: 1
revToRmlVersion: 1

libraries:
  bonhomme_eye:
    libraryId: 623
    fileId: 37316
    versions:
      1:
        libraryVersionId: 1645
        components:
          - { coreId: "0-2", type: artboard, name: "Eye", folder: bonhomme_eye@118810 }
      2:
        libraryVersionId: 1646
        description: "Black iris"
        components:
          - { coreId: "0-2", type: artboard, name: "Eye", folder: bonhomme_eye@118811 }

folders:
  bonhomme_eye@118810:
    library: bonhomme_eye
    assetId: 118810
    imports: []
  bonhomme_head_and_hat@118813:
    library: bonhomme_head_and_hat
    assetId: 118813
    imports:
      - bonhomme_eye@118810
```

**`lockVersion`** — how this file is spelled. A build that reads a different
one refuses the project rather than guessing, because reading it with the
wrong rules would answer the published-component check on nonsense. Deleting
`.libraries` and pulling again is the remedy.

**`revToRmlVersion`** — which build's conversion the folders are. A snapshot is
the markup this build makes of those bytes, not the bytes, so a build whose
conversion differs downloads them again.

**`libraries`** — what each published version holds. The key is the library's
name as the project spells it, matching the `libraries:` block in `rive.yaml`.
Each version lists its components by their core id, type and name, and for
each one, the folder carrying it.

That last field is the point of the section. **A version spans as many
snapshots as it has publishes behind it**: a publish that touches one
component leaves every other pointing at the snapshot of the publish that last
touched it. So a component's folder is per component, not per version.

**`folders`** — one row per snapshot on disk: which library owns it, its
snapshot id, and the snapshots its own markup imports. The `imports` list lets
a pull walk the graph without reading markup.

## What a pull does with it

A snapshot's id names bytes that can never change, because a publish writes
that id once and the asset store keys content by its own digest. So a folder
an earlier pull wrote for that id is still correct, and a later pull keeps it
rather than downloading it again.

What that does not cover is the conversion, which is what `revToRmlVersion` is
for, and the shape of the lock itself, which is what `lockVersion` is for. A
mismatch in either throws the folders away.

A pull that cannot reach some library writes what it did reach and reports the
rest. It never deletes a folder it merely failed to hear about.
